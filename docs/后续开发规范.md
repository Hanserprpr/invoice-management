## 3. 总体开发原则

### 3.1 纵向闭环优先

不得按照 42 张表逐表生成无业务约束的 CRUD。开发应围绕业务闭环分阶段进行，每一阶段必须包含数据库、服务、接口、权限、测试和审计要求。

第一条必须打通的业务链路为：

```text
OIDC 登录
→ 获取并选择社团
→ 创建项目
→ 发布申请表
→ 创建并提交申请
→ 上传和确认发票
→ 社团逐票审核
→ 查看台账
```

### 3.2 服务端是规则最终执行者

前端校验只用于改善交互。租户归属、角色权限、状态迁移、金额范围、重复提交、版本冲突等规则必须由服务端再次校验。

### 3.3 默认拒绝跨租户访问

任何包含租户业务数据的请求，都必须同时满足：

1. 用户已通过 OIDC 登录；
2. 请求携带合法的 `X-Organization-Id`；
3. 用户在该社团存在当前有效且状态为 `ACTIVE` 的成员关系；
4. 用户具有当前操作所需角色或项目范围；
5. 被操作资源的 `organization_id` 与当前租户一致。

不能仅凭前端传入的资源 ID、成员 ID 或项目 ID 推断访问权限。

### 3.4 状态变化必须通过领域服务

项目、申请、发票、审核、纸票和导出批次的状态禁止由通用更新接口任意修改。状态变化必须使用语义明确的服务方法，例如 `submitApplication`、`approveInvoice`、`receivePaperInvoice`。

### 3.5 历史记录不可覆盖

表单版本、申请修订、发票文件修订、审核结论、纸票事件、平台外状态事件和导出产物应追加新记录，不得覆盖历史事实。确需更正时，应生成更正事件并保留原记录。

## 4. 开发阶段与准入门槛

后续工作必须按以下阶段推进。前一阶段验收未通过时，不进入后一阶段的大规模开发。

### 4.1 阶段 D0：数据库可运行化

目标：让新环境可以使用一条标准命令得到一致的数据库结构和最小基础数据。

必须完成：

- 引入 Flyway，关闭依赖 ORM 自动建表的可能性；
- 将 `docs/mysql.md` 中的 42 张表转换为 `V1__init_schema.sql`；
- 建立后续迁移文件命名规则：`V{版本号}__{英文说明}.sql`；
- 初始化系统角色、权限、角色权限关系和基础字典；
- 设计首个用户或平台管理员的安全开通方式；
- 提供仅用于本地/测试环境的最小数据，不得混入生产迁移；
- 校验 PO 字段、主键策略、非空约束、唯一索引、外键和乐观锁字段；
- 明确数据库字符集、时区和金额精度。

迁移规范：

- 已在共享环境执行过的迁移文件禁止修改，只能追加新迁移；
- 结构迁移不得包含真实人员信息、真实票据或密钥；
- 初始化角色和权限必须使用稳定编码，不依赖自增 ID；
- 测试数据放在测试资源或独立开发配置中；
- 生产环境不得启用自动插入测试用户的逻辑。

验收条件：

- 空 MySQL 数据库可完成全部迁移；
- 重启应用不会重复插入数据或破坏结构；
- 42 张表、索引和外键与设计文档一致；
- OIDC 登录所需的测试用户和成员关系可在非生产环境安全初始化；
- 数据库集成测试通过。

### 4.2 阶段 D1：认证、租户和权限闭环

目标：用户登录后只能看到和操作自己有权访问的社团及资源。

必须实现的基础接口：

| 接口 | 用途 | 租户请求头 |
|---|---|---|
| `GET /auth/me` | 获取当前登录用户 | 不需要 |
| `GET /api/organizations` | 获取当前用户有效社团列表 | 不需要 |
| `GET /api/organizations/{id}` | 获取当前社团详情 | 需要 |
| `GET /api/organizations/{id}/members` | 分页查询成员 | 需要 |
| `POST /api/organizations/{id}/members` | 新增或开通成员 | 需要 |
| `PATCH /api/organizations/{id}/members/{casId}` | 修改成员状态或任期 | 需要 |
| `PUT /api/organizations/{id}/members/{casId}/roles` | 分配成员角色和范围 | 需要 |

权限要求：

- 建立平台管理员、社团管理员、项目负责人、审核人和普通成员的服务端权限判断；
- 社团列表接口只能按当前 `cas_id` 查询，不得关闭租户拦截后返回全量数据；
- 平台管理员跨租户操作必须走独立、显式、可审计的入口；
- `@InterceptorIgnore(tenantLine = "true")` 只能用于经过安全审查的全局查询；
- 每个忽略租户拦截的查询必须自行包含用户、组织或平台权限条件；
- URL 中的 `{id}` 必须与 `X-Organization-Id` 一致，否则拒绝请求；
- 成员离任、过期或被停用后，应立即失去租户访问权限。

OIDC 约束：

- `casID` 是系统用户主键和登录主体，不再另外生成用户业务 ID；
- 系统仅信任 OIDC 返回的身份声明，不接收客户端自行提交的 `cas_id` 作为登录身份；
- 未开通用户默认拒绝登录，不允许未经审批自动加入社团；
- 姓名可在登录时从受信任的 OIDC 声明同步；
- 生产环境必须使用 HTTPS，OIDC 密钥只通过环境变量或密钥服务注入；
- 后续如引入 Redis 会话，必须验证退出、过期和多实例一致性。

验收条件：

- 用户能完成登录、查看社团、选择社团和访问社团详情；
- 无成员关系、成员过期、成员停用和伪造租户头均被拒绝；
- 两个社团使用相同资源 ID 场景下仍不能发生越权；
- 关键授权路径具备自动化测试；
- 所有拒绝结果使用统一 HTTP 状态和业务码。

### 4.3 阶段 D2：MVP 核心收集链路

当前进度：项目管理、动态表单，以及申请草稿、自动保存、历史版本绑定、条件答案校验、提交窗口/次数限制、修订历史、乐观锁和审计已完成；文件上传、发票及其派生申请状态尚未实现。

目标：在不依赖 OCR 和复杂导出的前提下，通过人工录入先完成一条可用主链路。

开发顺序：

1. 项目管理：创建、编辑、开放、关闭和归档；
2. 动态申请表：草稿、版本发布和不可变历史版本；
3. 申请管理：草稿、答案保存、提交、修订和提交次数限制；
4. 发票管理：人工录入、文件关联、金额校验、提交和作废；
5. 社团审核：开始审核、通过、退回、拒绝和复核历史；
6. 发票台账：分页、筛选、排序和单票聚合时间线。

实现约束：

- Controller 仅负责协议转换和参数校验；
- Service 负责权限、状态、事务和业务规则；
- Mapper 不承载跨领域业务决策；
- 接口使用请求/响应 DTO，不直接把 PO 作为对外协议；
- 创建业务实体使用服务端生成的 ULID；
- 金额统一使用 `BigDecimal`，禁止 `double`；
- 时间统一保存为 UTC，接口使用带时区的 ISO 8601 格式；
- 更新版本化实体时必须检查 `version`，冲突返回 `VERSION_CONFLICT`；
- 提交、审核和批量操作必须考虑重复请求，必要时使用幂等键；
- 多表状态变化必须放在同一事务中；
- 列表接口必须分页，并设置服务端最大分页大小。

验收条件：

- 一个社团、一个项目、一个表单版本可完成申请和发票提交；
- 审核人可以逐票通过、退回或拒绝；
- 被退回的发票可以形成新修订后重新提交；
- 台账能查询完整、正确且仅属于当前社团的数据；
- 状态机的非法迁移全部被服务端拒绝；
- 核心 Service 和接口具有正常、边界及越权测试。

### 4.4 阶段 D3：文件、识别、规则和纸票

目标：补齐发票材料处理和社团整理能力。

必须完成：

- 文件上传、下载、元数据、SHA-256、类型和大小限制；
- 对象存储路径必须包含不可伪造的租户隔离信息；
- 下载文件前必须重新校验租户和资源权限，不能只依赖 URL 隐蔽性；
- OCR 和二维码识别通过适配器接口接入，失败时允许人工录入；
- 识别原文、结构化建议和人工确认结果分别保存；
- 精确查重和疑似查重规则；
- 规则集、规则版本、字典版本的发布和历史保留；
- 项目启用纸票时的收取、退回、遗失、更正及扫码事件。

异步任务要求：

- OCR、材料包生成等耗时操作通过 `async_job` 管理；
- 任务必须携带 `organization_id`，工作线程执行前显式恢复租户上下文；
- 任务重试不能产生重复文件、重复审核或重复通知；
- 记录失败原因、重试次数和最终状态；
- 外部服务不可用时应降级，不阻断人工完成主流程。

验收条件：

- 文件不能被其他社团下载或枚举；
- OCR/扫码失败可降级为人工录入；
- 完全重复发票不能内部通过，疑似重复必须提示人工确认；
- 规则和字典发布后历史申请仍引用原版本；
- 纸票关闭的项目不能调用纸票相关操作。

### 4.5 阶段 D4：导出、外部状态、通知和审计

目标：完成从社团内部审核到校外流程记录和材料交付的闭环。

必须完成：

- 仅将内部通过、同一项目且未被其他活动批次占用的发票加入导出批次；
- 导出批次保存发票快照，重新生成时创建新版本，不覆盖旧产物；
- 默认生成 XLSX、清单 PDF、附件 ZIP 和带 SHA-256 的 `manifest.json`；
- 平台外状态使用追加事件，更正时引用原事件；
- 待办与通知具备去重、已读和失败重试策略；
- 关键业务操作写入不可修改的审计日志；
- 换届交接后，历史数据归属于社团而不是原负责人个人。

验收条件：

- 同一张发票不能同时进入两个未结束导出批次；
- 导出材料可验证完整性且能追溯生成版本；
- 平台外状态更正不会覆盖原事件；
- 关键创建、修改、审核、导出和授权操作均可审计；
- 新负责人可在授权后继续访问社团历史项目。

### 4.6 阶段 D5：试点和上线准备

必须完成：

- 使用脱敏发票样本完成二维码和 OCR 回放；
- 完成 PRD 第 18 章的端到端验收场景；
- 执行跨租户、水平越权、文件下载、批量接口和管理员入口安全测试；
- 验证数据库备份、恢复和迁移回滚预案；
- 验证多实例下会话、异步任务和幂等行为；
- 建立生产环境配置清单和密钥轮换方式；
- 为关键接口设置超时、限流、日志和监控；
- 清理测试账号、测试密钥和开发环境数据。

## 5. 代码组织规范

业务模块建议保持以下职责分层：

```text
controller   HTTP 协议、参数校验、Result 返回
service      权限、业务规则、事务、状态机
mapper       数据访问和必要的安全限定查询
data/po      数据库持久化对象
data/dto     接口请求对象
data/vo      接口响应对象
data/enums   状态、类型和业务码
security     登录主体、方法授权和安全异常处理
tenant       租户上下文、过滤器和租户辅助能力
```

新增模块时，应优先按业务域组织清晰的类名，避免出现承载所有逻辑的通用 `CommonService` 或超大 Controller。

## 6. API 统一约定

- API 业务路径统一使用 `/api` 前缀；
- 登录协议入口使用 `/oauth2`、`/login` 和 `/auth`；
- 租户业务请求统一使用 `X-Organization-Id`；
- 成功和失败业务响应统一使用 `Result<T>`；
- HTTP 状态必须表达协议结果，不能所有错误都返回 HTTP 200；
- 参数错误返回 400，未登录返回 401，无权限返回 403，资源不存在返回 404，版本或状态冲突返回 409；
- 系统异常通过全局异常处理器转换，禁止向客户端返回堆栈、SQL 或密钥信息；
- 列表接口统一返回分页结构，至少包含 `records`、`page`、`pageSize` 和 `total`；
- 批量接口必须设置数量上限，并返回逐项结果或明确的原子性语义；
- 修改接口不得通过空值含义猜测“保持不变”或“清空”，DTO 必须表达明确语义；
- 文件和异步任务接口应返回稳定资源 ID，由状态查询接口获取进度。

## 7. 事务、并发和幂等规范

- 一个业务动作涉及多表写入时，由 Service 层开启事务；
- 不在数据库事务中执行长时间 OCR、压缩、网络下载等外部调用；
- 有 `version` 字段的实体必须使用乐观锁更新并检查影响行数；
- 创建导出批次、提交申请、审核和批量操作必须防止并发重复执行；
- 客户端可重试的写操作使用 `Idempotency-Key`，服务端通过 `idempotency_record` 保存结果摘要；
- 唯一约束冲突必须转换为稳定业务码，不能直接泄露数据库异常；
- 异步任务采用“至少一次执行”假设，处理器必须具备幂等性。

## 8. 审计与日志规范

以下操作至少记录操作者 `cas_id`、`organization_id`、资源类型、资源 ID、动作、结果、时间和必要变更摘要：

- 社团成员开通、停用及角色变更；
- 项目开放、关闭和归档；
- 表单版本发布；
- 申请提交和撤回；
- 发票关键字段更正和作废；
- 审核通过、退回和拒绝；
- 纸票人工状态修改；
- 导出批次创建、生成、取消和下载；
- 平台外状态记录和更正；
- 平台管理员跨租户操作；
- 换届交接。

日志中不得记录 OIDC 密钥、Cookie、会话令牌、完整发票图片内容或其他不必要的敏感信息。

## 9. 测试规范

每个业务阶段至少包含：

- 领域服务单元测试；
- Mapper 与 MySQL 的集成测试；
- Controller 接口测试；
- 合法状态迁移和非法状态迁移测试；
- 同租户正常访问和跨租户拒绝测试；
- 不同角色的允许/拒绝测试；
- 乐观锁冲突、重复提交和幂等测试；
- 外部依赖超时、失败和降级测试。

不允许仅使用 H2 代替 MySQL 验证 SQL。涉及索引、JSON、字符集、约束和事务行为的测试应运行在与生产主要版本一致的 MySQL 上。

## 10. 完成定义

一个功能只有同时满足以下条件才可标记完成：

- 对应 PRD 验收标准已实现；
- 数据库迁移和实体映射已同步；
- 接口 DTO、业务码和异常行为明确；
- 租户、角色、项目范围和资源归属校验完整；
- 状态、事务、并发和幂等规则已落实；
- 必要审计日志已记录；
